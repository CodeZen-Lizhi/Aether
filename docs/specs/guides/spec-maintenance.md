# 初始化与维护 Spec

## 初始化后的第一轮

文档骨架不代表规范已经匹配业务。直接要求 Agent：依据真实代码、现有测试、构建配置和已确认约定，建立或补齐 `docs/specs/` 中的项目规范。

1. 确认当前项目与工作区状态，保护已有规则；从 manifest、入口和代表性调用链识别实际包与层。
2. 先覆盖正在开发的关键路径。共享审查/验证规则只写一份，模块文档记录自己的契约、例外和证据，不按模板强制生成同样五个文件。
3. 用全局约定和对应 Review 技能检查风险遗漏；这些是规范性要求，不能据此声称项目已有某个接口、事务或中间件。空项目只记录已确定的目标约束，其余等首个真实功能落地。
4. 删除纯模板，保留混合文件里的有效内容；检查索引、任务上下文引用和示例路径。已有历史契约与代码冲突时追踪当前权威来源，标清替代关系。
5. 文档验证检查链接、真实符号、Schema 来源和可执行命令。没有运行测试就不写测试通过；单纯更新 Spec 无需全量构建。

## 日常增量更新

在功能、bugfix 或重要设计决策完成后，直接更新 `docs/specs/` 中受影响模块的文档。记录稳定且值得复用的事实：输入输出、失败边界、事务/权限/重试语义、兼容性和对应验证入口。一次性排障输出放任务记录，不塞入长期 Spec。

先复用本次已经验证的代码和测试，再补缺口。规则变更就修改原来的权威段落，同时删除失效说法；没有新知识时无需为了完成流程制造文档。新增、改名或删除文件时同步索引与需要继续执行的任务上下文。

## Aether 的入口

- 开发前：从 [总索引](../index.md) 找包索引与专门业务契约。
- 共用风险与验证：读 [后端质量规范](../backend/quality-guidelines.md) 或 [前端质量规范](../frontend/quality-guidelines.md)。
- 开发流程：使用全局 `delivery`，按任务范围读取共享工程规范和本项目规范，完成后按已验证的变化维护文档。
- 规范结构调整后：检查索引、链接和有效规则是否保留，只合并有价值变化。不要直接套用另一项目的业务规范。

## 按需配合其他技能

需要设计模块边界时，按实际可用的设计技能限定模块并形成可审阅建议；拆解大功能时，由 `delivery` 组织可独立验收的交付单元，必要的计划与结果写入 `docs/tasks/`。其他技能仅在可用且符合调用条件时使用。结论只有被采纳、落地或明确成为约束后，才进入长期 Spec。
