# 首次响应之后的错误处理与配置建议

状态：研究建议与决策记录。用户已选择本次不加静默高级配置，未修改产品代码。

## 依据与边界

- 用户已经确定：上游成功响应头结束首次等待；不能继续等实际文本或压缩结果才解除首次期限。最新询问是在此基础上是否增加更好的错误处理/高级配置。
- `apps/aether-gateway/src/execution_runtime/stream/execution.rs:5470` 明确描述 HTTP 200 后仍可能出现 `response.failed`，现有预读用于保留候选切换机会；首次计时和下游提交不能再通过同一个“首有效输出预算存在”条件隐式绑定。
- `execution.rs:6768` 处理运行期执行错误帧；`:6896` 附近在失败后按支持的协议发送终结错误事件。解除首次计时不意味着删除这些检查，也不意味着把 HTTP 200 写成整条请求成功。
- `execution_failures.rs:553`、`:655`、`:771` 有预提交供应商错误/执行错误/传输故障的候选重试路径；重试仍须满足原有错误分类、重试次数和剩余期限约束，不能因客户端未见输出就把任何失败自动重放。
- `execution.rs:6758` 的 EOF 分支对 Anthropic 缺失 message_stop 显式判失败，不能据此声称所有协议都已覆盖“干净 EOF 但缺失正常完成事件”。Responses 等受影响路径需要定向验证其最终归并/完成标记语义。
- `execution_runtime/transport.rs:2944` 对流式请求跳过非流式完整期限；`:4059` 附近客户端构建同样对流式跳过 total_ms。旧首输出预算在有效内容后解除。新增完整流式期限必须实际覆盖生成/转发阶段，不能仅改设置名称。

## 推荐的最小配置模型（建议，非新增授权）

1. 基础项“首次响应超时”：限制一次上游尝试开始到收到最终成功响应头；非成功状态及时走错误策略，1xx 等临时响应不应无限续期。继续保留短等待以便无响应时较快失败或切换。
2. 基础项“流式请求总超时”：从逻辑请求开始覆盖全部尝试和输出阶段；重试、心跳、HTTP 200 都不重置。与首次期限独立；必要时允许压缩单独覆盖完整期限，不扩大普通请求首次等待。
3. 可选高级项“上游静默超时”：默认关闭；开启后按上游连续无数据时间判断，不要求有效内容。上游真实事件/心跳可重置，网关自己向下游发心跳不可重置。开启有助于更快结束挂起，也可能误伤长时间静默的正常压缩。
4. 本次不推荐增加“首有效输出超时”开关；首有效内容时间用于诊断/指标即可，避免重建当前语义冲突。开源功能数量不等于本项目的必要配置数量。

## 错误处理建议

- 明确错误事件、可检测的网络异常应立即进入失败处理；不等总期限。缺失完成标记按各协议定义识别，不能一律把 HTTP 200 + EOF 当成功。
- 对“连接保持、没有错误、没有数据”的情况，网关没有足够信号区分慢处理与挂起；由总期限兜底，可选静默期限只是更激进的策略，不是可靠的远端故障证明。
- 上游 HTTP 响应与向客户端提交 HTTP 响应是两个独立边界。尚未提交给客户端时，可按已有策略执行允许的候选切换；已经提交后不能回改 HTTP 状态码或无缝拼入另一供应商回答，应按协议报告流内错误并记录真实失败。自动重放还需考虑工具/副作用与重复执行，不能承诺“尚无可见输出就一定可安全重试”。
- UI 独立展示已收到响应/处理中、首批数据时间和整体终态；候选失败重试中保持请求进行中，最终错误同时更新列表与详情，并指明首次等待、总期限或上游错误的真实类别。

## 用户决定

用户回复“先不加了”：本次不加入上游静默超时高级选项，挂起请求由独立完整期限兜底。上面的可选静默建议保留为研究背景，不是本次实现要求；首有效内容期限同样不新增。独立完整期限的初始默认值仍需确定。
