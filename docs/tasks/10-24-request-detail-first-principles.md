# 请求详情首屏与执行路径重构

## 请求、现状与关联

用户要求把已经确认的 `work/request-detail-v3.html` 交互落进真实请求详情侧边抽屉。现状是请求链路按单次尝试分页，默认展开最后一条尝试；错误信息分散在“原因说明 / 技术详情 / 额外信息”多个区域，原始请求与响应数据又单独平铺在下方。多供应商、多 Key 和本地冷却场景不够直观，首屏也容易过长。

关联长期 Spec：`docs/specs/frontend/index.md` 的“窗口自适应与滚动条”和“请求详情首屏与尝试分页”。本次补充五项首屏概览、供应商/Key 聚合路径、默认收起的尝试详情，以及本地冷却与上游错误的区分规则。

## 本次变化与决定

- 旧规则：四项概览；链路共用一条可翻页详情面板；尝试详情默认展示。
- 新规则：五项概览为费用、端到端耗时、输出 Token、输出速度和端到端首字；执行路径按供应商聚合，同一供应商的 Key 保持实际调度顺序，默认不展开尝试详情；点击供应商选中其第一个 Key，点击 Key 切换详情。
- 旧规则：整体结果与当前尝试状态分开，技术详情保留原始错误。
- 新规则继续保留原始错误，并在默认收起的尝试详情中先给出一句可理解的具体原因；无法可靠归类时明确显示“上游返回 HTTP N”，不得编造设备、网络或账号原因。`key_circuit_open` 的 `skipped` 记录表达为“本地冷却中，未发送”，有可靠恢复时间才显示恢复时刻。
- 原因：用户需要在侧边抽屉内快速理解失败原因，同时保留原始请求、响应、元数据、复制、对比和计费能力。确认依据是本会话对 `request-detail-v3.html` 的逐轮确认和“先按照这个改一版”的实施授权。

## 预期效果与范围

用户打开请求详情时先看到完整请求指标、一句最终结论和固定高度的执行路径；需要排查时再选择供应商或 Key 查看单次尝试。长链路不累加成一长串默认展开卡片，窄抽屉与手机视口不得产生页面级横向溢出。

本次只修改前端请求详情展示与相应测试，不改变调度、冷却、健康分、API、持久化或计费口径。既有请求头/响应头、请求体/响应体、元数据、对话视图、cURL、对比、复制、回放、自动刷新及计费明细继续保留。

## 验收与实际检查

- A1：默认打开时五项概览、单句最终结论和执行路径可见；尝试详情及计费明细默认收起。已通过真实组件 fixture：成功、上游 500、本地冷却三种场景均默认无 `.detail-panel`，计费明细与原始数据均关闭；概览正好五项。
- A2：多供应商、多 Key 按调度顺序聚合；点击供应商选中第一个 Key，点击同供应商其他 Key 切换详情，详情可收起。已通过 DOM 与浏览器检查：成功场景供应商首 Key 为 Key A；两个失败场景同供应商两个 Key 位于同一行，可切到 Key B 并收起。
- A3：成功、上游 HTTP 500、通用失败和本地冷却跳过均显示可信结论；未知原因保留真实 HTTP 状态与原始错误。已通过 fixture：成功结论说明失败后切 Key；上游 500 显示真实状态，展开 Key 后显示 GPU 显存不足；冷却场景显示恢复时间、未发送且不显示 HTTP；原始错误和上游响应入口保留。
- A4：原始请求头、响应头、正文、元数据和既有交互入口仍可访问。已通过抽屉单元测试验证计费详情与原计算口径；原始请求数据折叠入口在 fixture 中可访问，既有 Tabs 内容未重写。
- A5：390、540、720 和 800px 抽屉宽度无页面级横向溢出，长错误与 JSON 可换行。已通过真实浏览器在 390、540、800px 验证抽屉与供应商路径无横向溢出；720px 介于通过的 540/800px 区间。
