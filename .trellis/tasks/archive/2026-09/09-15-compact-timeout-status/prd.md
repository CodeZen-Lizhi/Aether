# 修复流式首次响应超时与重试状态一致性

状态：in_progress。用户在最终方案后明确批准实施，900 秒默认值与兼容方式已确认；不修改生产配置。

## 目标

普通 HTTP 流式会话和流式压缩收到上游成功响应头后即可继续等待结果，不再被首有效内容计时误杀；请求列表与详情准确反映整个请求及每次尝试的状态。

## 需求与验收

### R1：请求状态一致

1. 尚在重试的请求，列表/卡片/详情总状态保持进行中；失败只标在对应尝试节点。HTTP 200 后出现流内错误仍按实际结果失败。
2. 整条请求终结后，所有入口和关闭重开、刷新、轮询一致显示终态；失败展示逻辑请求耗时与最终原因，不把单轮 180 秒冒充整条请求的 300 秒。
3. 保留真正终态的防陈旧更新保护、历史无生命周期记录的兼容和图片显式失败信号。
4. 验收覆盖第一轮失败、重试间隙、第二轮开始、最终成功/失败，经 records/detail/trace API 与前端合并读取证明一致。

### R2：首次响应与完整响应期限分离

1. 单轮首次响应限制在收到上游最终成功响应头（例如 HTTP 200）时解除；不必等待非空 body、启动事件、文字或压缩结果。非成功状态及时走错误策略，临时 1xx 不结束首次等待。
2. 成功响应头到达后，候选 watchdog、底层首 body 等待和旧首有效输出预算均不得继续取消当前请求；后续只由独立完整响应期限及实际错误/取消结束。普通流式与压缩相同。
3. 配置显示“首次响应超时”和“流式请求总超时”。首次值沿用当前配置及 30 秒缺省，不批量提高已保存值。总期限默认为 900 秒（15 分钟），支持按供应商设置 1–1200 秒，清空恢复缺省；普通流式和压缩共用。
4. 总期限从逻辑请求开始计时，覆盖选择、重试、等待和响应体生成/转发；收到响应或重试都不重置。首次确定执行供应商时绑定其总期限，后续切换不得延长原截止时间。
5. 不把旧 stream_failover_budget_ms 的默认 90 秒或已保存值变成整段回答上限；新 HTTP 聊天流链路退出旧首有效输出计时。旧配置数据保留以兼容旧读写/回退，管理表单明确采用新总期限；非流式 request_timeout 保持原语义。
6. 响应头时间、首 body 时间、首有效内容时间和整体结束时间分开记录，文案说明计时口径。HTTP 200 只表示已响应，不能直接写为业务成功。
7. 验收：首次阈值 1 秒，上游 100 ms 返回 HTTP 200，3 秒后才有 body/文字或压缩结果，总期限 5 秒时成功；旧 1.8 秒首输出预算不能截断。早期心跳后静默再成功同样通过。
8. 对照：始终没有响应头会首次超时；只有响应头后不再返回数据、或持续有数据但超过整体期限，都按总超时终结。总超时后检查候选和 usage 终态、资源释放及后续请求可用。

### R3：保留错误检测与安全重试边界

1. 解除首次计时和向客户端提交响应分离；保留现有协议错误预读与完成标记检查，不通过判断 deadline 是否存在来意外关闭错误检测。
2. 明确流内错误、连接异常、协议要求的终态缺失按现有协议处理；已交付协议/工具/模型状态后不透明重放或拼接第二次生成。HTTP 成功不替代业务完成。
3. 尚未提交的失败仅按已有错误分类、尝试次数及剩余总期限切换；取消不记为供应商失败。超时和终态持久化有唯一归属，不能重复结算或被同一计时器取消。
4. 验收覆盖 HTTP 200 后早期 error、已交付内容后 error/断开、提前 EOF、客户端取消、总期限与正常完成同时发生的边界。支持协议内错误反馈时保留，已发送的 HTTP 状态不回改。

## 范围与限制

- 本次不加静默超时、首有效内容超时、压缩专属期限、模型/推理强度/上下文裁剪调整。
- HTTP 聊天流及其普通/压缩请求为超时修复范围；图片/视频、非流式 compact、Responses WebSocket 的独立期限保持原语义。隧道承载上述 HTTP 请求时属于覆盖范围。
- 不重放真实会话、不改本机供应商生产配置。提交、安装、发布不包含在这次代码修复请求中。
- 供应商明确错误或独立总期限耗尽仍会失败；本任务不承诺所有压缩成功。15 分钟是可调默认策略，不是性能保证。
