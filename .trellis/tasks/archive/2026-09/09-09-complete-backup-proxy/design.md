# 设计与已验证事实

- 已用真实 Pinia store 复现：先加载空列表，再导入成功，列表仍为空，两个导入入口都报红。
- 已用两个临时 SQLite 实例复现：代理地址相同但 ID 不同，供应商引用会重映射，`system_proxy_node_id` 仍指向源 ID。列表 API 此时能读到实际导入节点。
- 节点列表服务端没有默认状态过滤；前端 `ensureLoaded` 永久沿用已加载空列表，导入成功没有刷新。
- 现有导出包含供应商、Endpoint、Key、模型及代理配置，但渠道元数据、运行状态与累计用量未进入备份 DTO。

沿用现有事务和无版本 JSON 契约。所有代理设置用同一引用校验/重映射逻辑；补齐现有渠道记录的字段，并在备份事务内恢复，普通管理员编辑仍保留其并发更新边界。前端在提交成功后失效缓存、刷新节点与配置，刷新失败单独展示；密码恢复使会话失效时等待重新登录。对未包含新增字段的历史文件保留兼容。

排查使用自动化合成数据，没有读取真实代理凭据或修改真实库。已通过最小复现区分 UI 缓存与数据库恢复，无需额外日志或生产探针。
